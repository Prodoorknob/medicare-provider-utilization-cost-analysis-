How to use this library

Each report is self-contained and answers the questions an interviewer is likely to push on for that layer. They are organized by what was actually hard to learn or ship, not by what is obvious from the code. Open any one cold and you should be able to talk for ten minutes. The final critique report is the one to read after the others, since it assumes you remember the architecture.

Project status — complete & in maintenance (June 2026)

The nine reports below are preserved as written (April 2026). The project has since been completed and moved to maintenance mode. The main developments after these reports:

  • Data layer migrated Supabase → Railway Postgres (the serving notes in Report 07 predate this).
  • The anomaly agent (Report 09) became the project’s center of gravity — now 11 rules, 8 evaluable, with the Stage 1 model repositioned as a fraud input (a REVENUE_DEVIATION residual rule). The ML/forecast tracks are now enhancements, not the headline.
  • Built a validation harness against government ground truth (OIG LEIE + the new CMS Revoked Providers list). An independent review then found the first backtest had look-ahead and selection-on-test leakage; the leakage-corrected, point-in-time, held-out, volume-stratified evaluation gives the honest verdict: a modest ~2–4× deep-k lift with a ~3.5-year lead time, but largely a volume confound — a useful screening prioritizer, not a validated fraud detector.
  • Security hardening: the /investigations route is gated and no-indexed, NPI redaction defaults on, and the published briefs are masked.
  • The monthly validation loop is deployed as a Railway cron service, running independent of any local machine.
