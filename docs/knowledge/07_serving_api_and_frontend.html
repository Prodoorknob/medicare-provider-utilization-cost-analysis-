Two-tier serving architecture

The app has a dual backend: Railway for live model inference, Supabase for precomputed lookups and reference data. The frontend calls the Railway FastAPI, which itself queries Supabase for reference data (labels, state summaries, metrics). This lets the frontend stay thin and avoids exposing Supabase keys to the browser.

Next.js 16 (Vercel) │ └─► FastAPI (Railway) ──► LightGBM booster (in-memory, startup load) │ 3 CatBoost OOP models (in-memory) │ label_encoders.json (dict lookup) │ hcpcs_target_enc.json (dict lookup) │ └─► Supabase Postgres (REST, anon key) ├─ lookup_labels (dropdown options) ├─ stage1_allowed_amounts (32,818 precomputed groups) ├─ stage2_oop_estimates (23,424 precomputed groups) ├─ lstm_forecasts (62,703 rows) ├─ state_summary ├─ model_metrics ├─ feature_importances └─ specialty_yearly_avg (for forecast trend chart)

The precomputed tables were aggregated from local_pipeline/ parquets with Python scripts that pushed via Supabase REST. Auth is row-level security with public SELECT; no writes from the browser.

Model loading at startup

The FastAPI lifespan hook in api/main.py:13-23 calls load_all_models() at process startup and attaches the result to app.state.models. All request handlers read from app.state.models and never hit disk. Deploy-time latency is ~2-3 seconds on Railway's small Postgres-plus-Python image.

Feature reconstruction at request time

Serving feature parity with training was the second-hardest piece of this project after data wrangling. The HCPCS bucketing code lives in two places and must agree: notebooks/03_gold_features_local.py:100-128 (training) and api/services/prediction.py:32-61 (serving). Any drift between them would silently corrupt predictions.

Stage 1 request flow

POST /predict/full (FullPredictionRequest) │ ▼ build_stage1_features() at api/services/prediction.py:64 1. Encode provider_type -> idx via artifacts.specialty_to_idx (fallback = N+1) 2. Apply config defaults for missing risk/volume/charge 5. Compute log_srvcs, log_benes, srvcs_per_bene 6. Compute specialty_bucket = specialty_idx * 6 + bucket 7. Compute pos_bucket = pos * 6 + bucket 8. Look up hcpcs_target_enc (fallback to global_mean 76.34) 9. Stage 2 request flow

Stage 1 output -> allowed_amount (passed into Stage 2) ▼ build_stage2_features() at api/services/prediction.py:179 - state -> census_region via STATE_TO_REGION (default South = 3) - All 12 features arranged in OOP_FEATURE_NAMES order - Categoricals cast to int ▼ catboost.Pool(features, cat_features=[2,3,4,5]) ▼ p10 = oop_p10.predict() p50 = oop_p50.predict() p90 = oop_p90.predict() ▼ Asymmetric CQR widening (loaded from oop_calibration.json): p10 = p10 - artifacts.oop_q_lo (q_lo = +$0.0004 today; ~no-op) p90 = p90 + artifacts.oop_q_hi (q_hi = +$14.4710 today) ▼ Floor at 0, enforce non-crossing: p50 = max(p10, p50); p90 = max(p50, p90)

The no-charge model auto-detection at api/services/prediction.py:117-131 is the subtle piece: the API does not know at build time whether the ops team shipped the with-charge or no-charge LightGBM, so it inspects booster.feature_name() and includes Avg_Sbmtd_Chrg conditionally. This made the no-charge deployment swap a zero-code change.

Why Railway and not Vercel serverless

ConcernVercel serverless PythonRailway container
Cold startLoad 4 models on every cold boot (~3s per request on first hit per region)Load once at container start, keep in memory
Bundle size250 MB function limit; LightGBM + CatBoost + pandas + numpy approach that ceilingNo limit
Process modelPer-request new interpreter; loader runs each time unless cachedPersistent process, uvicorn workers
Supabase accessHTTPS from Edge runtimeHTTPS from container, same

Railway won because model loading needed to happen once, and the container can live long enough to amortize the ~3 seconds of startup. The frontend remains on Vercel which plays to its strengths (static assets, edge caching, Next.js tooling).

Data-fetch layer

All frontend calls go through web/src/lib/queries.ts. Base URL is process.env.NEXT_PUBLIC_API_URL with fallback to http://localhost:8000. There are nine typed functions, one per API endpoint. Responses are typed in web/src/lib/types.ts.

There is no React Query, no SWR, no server-side fetching. I chose raw fetch plus useEffect / useState for simplicity. Caching is browser HTTP cache; pages re-fetch on mount. For this app (low-traffic portfolio) it is fine; for production traffic I would add SWR with a 5-minute TTL on reference endpoints.

The hybrid lookup-or-infer pattern

The current architecture has two inference paths and the frontend does not pick cleanly between them:

PathSourceWhen
Precomputed lookupSupabase stage1_allowed_amounts tableWhen the user's combination exists in the precomputed grid
Live inferenceRailway /predict/fullWhen the combination is novel, or user wants a custom risk / charge / volume input

Today the home page calls /predict/full unconditionally. The Supabase lookup tables are used by other pages (Explorer, forecast visualization). Combining them into a single "ask Railway, fall back to Supabase on timeout" pattern is backlog.

Limitations and what I would do differently

  • 1Add SWR or React Query with staleness-based caching on reference endpoints. Every page mount currently re-fetches labels; a 5-minute cache would drop label calls by ~95%.
  • 2Add structured logging and at least one metric dashboard. Right now failures show up as 500s in Railway logs with no correlation ID.
  • 3Write integration tests that hit the deployed Railway API with known inputs and assert known outputs. The feature-reconstruction code in api/services/prediction.py has no tests and silent drift between training-time gold logic and serving-time encoding would not surface until a user complaint.
  • 4Swap the forecast endpoint to serve the stacker parquet instead of the LSTM forecasts; the schema is compatible but the rows have not been uploaded yet (FRONTEND_TODOS.md item).
  • 5Add a geographic choropleth. It is the most visually obvious missing feature for a Medicare cost app.

30-second pitch

The serving layer is a two-tier split. A FastAPI service on Railway loads a LightGBM booster and three CatBoost quantile models into memory at startup and serves three prediction endpoints (Stage 1, Stage 2, and a full two-stage pipeline). A Supabase Postgres holds seven tables of precomputed aggregates (32,818 Stage 1 groups, 23,424 Stage 2 groups, 62,703 forecast rows) for fast lookup on common queries. The Next.js 16 frontend on Vercel calls the Railway API for live predictions and for reference data passthrough to Supabase. The subtle piece is feature-reconstruction parity: the HCPCS bucketing logic in the training gold notebook and the serving prediction service must agree exactly, and auto-detection of the loaded model's feature list lets me ship the no-charge LightGBM as a zero-code deploy swap.
