The CMS Physician dataset, in detail

The "by Provider & Service" dataset is a per-NPI per-HCPCS row for every Medicare-billing provider, broken out by place of service. Each year is a separate file from the CMS data API at data.cms.gov/api/1/datastore/query/.... The pull is paginated at 5000 rows; pull_medicare_data.py walks all pages and writes one CSV per year.

The raw file is geographically and clinically wide. To keep memory bounded for downstream pipelines, partition_medicare_data.py shards each annual CSV into {STATE}/{PROVIDER_TYPE}/data.csv and injects the year into the filename pattern. Then csv_to_parquet.py rewrites every shard as Parquet. After this step, the rest of the pipeline never reads CSVs.

Year is not stored in the original CMS file. It is reconstructed from the source filename via regex during partitioning. If anyone re-downloads but forgets to re-partition, the year column silently disappears and any temporal model breaks. This is documented but the failure mode is quiet.

Why a separate Provider Summary pull

The Provider Summary dataset has one row per NPI per year and includes Bene_Avg_Risk_Scre, the NPI-level HCC risk score. This is the only way to get patient acuity into Stage 1 without claim-level data. The "by Provider & Service" dataset does not carry it.

The pull is a direct CSV download from the CMS catalog (no API pagination needed). 11 years times ~470 MB equals ~5 GB of raw downloads. The join happens at the gold layer in notebooks/03_gold_features_local.py:133-160 on (NPI, year). Missing scores are imputed with the global median, which lands at ~1.0 by construction (the HCC scale centers on 1.0).

MCBS PUF and the constraints that forced synthetic data

The Medicare Current Beneficiary Survey is the only public source linking demographic context to OOP spending. pull_mcbs_data.py downloads the Survey File (2015 to 2022) and Cost Supplement (2018 to 2023) ZIPs, with --url overrides because CMS reorganizes their download URLs unpredictably.

Three constraints forced the dual-track architecture for Stage 2:

ConstraintWhy it mattersTrack A (PUF) handlingTrack B (synthetic) handling
No Census region in PUFRegion is suppressed for re-identification risk; we cannot model regional OOP variation from PUF aloneCrosswalk is national, joins on year onlyRegion assigned from state in the provider data, then OOP modulated by region
Survey File and Cost Supplement PUF_IDs do not overlapCannot link the same beneficiary across files; cannot join demographics to actual OOP at the person levelCost Supplement is self-contained (has its own demographics: CSP_AGE, CSP_SEX, etc.)generate_synthetic_mcbs.py samples demographics from real distributions and pairs them with provider rows
OOP is annual, not per-serviceStage 2 wants per-service predictionAggregate national OOP-to-allowed ratio used as a calibration targetPer-service OOP synthesized with hardcoded modulation factors (-85% dual eligible, -35% supplemental, +3% per chronic condition, log-normal noise)

The MCBS LDS would solve all three constraints. It costs $600 per module + DUA + 6 to 8 weeks. Out of scope for this build.

Known data quality issues

These are documented in DATA_SOURCES.md and MODELING.md. They are real and they show up in production.

CMS specialty names rename across years

Idx AName AYearsIdx BName BYears
16Cardiology2013-2015, 2017-202317Cardiovascular Disease (Cardiology)2016 only
28Colorectal Surgery (Formerly Proctology)subset29Colorectal Surgery (Proctology)subset
87Oral Surgery (Dentist Only)subset88Oral Surgery (Dentists Only)subset

Discovered 2026-04-19 while debugging the Forecast Explorer trend chart. Root cause is that LabelEncoder is fit on the union of all year strings, so a single clinical specialty splits into two encoded indices with disjoint year coverage. The forecast model then has a 1-year sequence for one index and a 10-year sequence for the other.

Frontend interim fix: TOP_SPECIALTY_IDXS in web/src/lib/v2-model-data.ts points at the richer-history index. Proper fix (canonicalization in silver) is backlog item #5 in MODELING.md.

gold versus gold_year on Drive

The original gold/ directory uploaded to Drive lacks the year column (it was stripped during an aggregation step). gold_year/ has it. V2_13 hit an Arrow schema error pointing at gold/. Always use gold_year/ for any temporal modeling.

IQR outlier removal at silver is global

In notebooks/02_silver_clean_local.py:36-59, IQR is computed once across every state and applied uniformly. This penalizes legitimately expensive surgical and DME procedures because the bound is dominated by E&M codes. A within-bucket IQR would be cleaner.

What I would do differently on the data layer

  • 1Canonicalize specialty names in silver before encoding. Strip parenthetical aliases, normalize pluralization, then fit LabelEncoder. Would fix the Cardiology / Colorectal / Oral Surgery split and any others I have not audited.
  • 2Preserve NPI through gold. Dropping it killed any chance of integrating NPPES, AHRF (via ZIP), or building the provider anomaly agent in PROVIDER_ANOMALY_AGENT_SPEC.md.
  • 3IQR per hcpcs_bucket, not global. Or Winsorize at P1/P99 instead of removing rows so the gold count stays predictable.
  • 4Compute year as a column at ingestion, not derive it from filename regex. Make the failure loud if it goes missing.
  • 5Add a Pandera schema check at each medallion boundary. Even assert "Avg_Mdcr_Alowd_Amt" in df.columns would catch the gold/gold_year mistake earlier.

30-second pitch

The training data is CMS Physician and Other Practitioners 2013 to 2023, about 103 million rows pulled through the CMS data API and partitioned by state. I separately pull the Provider Summary dataset to join in NPI-level HCC risk scores. For Stage 2 I use the public MCBS Cost Supplement PUF, but the PUF has three constraints (no Census region, non-overlapping IDs across files, annual not per-service OOP) so I built a synthetic per-service OOP generator that samples demographics from real PUF distributions and modulates OOP by dual eligibility and supplemental status. The synthetic file is a drop-in replacement for the real MCBS LDS if a researcher gets DUA access.
